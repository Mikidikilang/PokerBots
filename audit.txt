2. Neural Network Capacity & Architecture — Score: 9 / 25
src/model/networks.py — the dead sequential encoder
src/training/sequential_history.py implements LSTMHistoryEncoder and TransformerHistoryEncoder. These are architecturally correct. They are never imported or used anywhere in the training pipeline. The PokerActorCritic uses HistoryEmbedding — a flat MLP over a 18×13 concatenated vector:

# networks.py
class HistoryEmbedding(nn.Module):
    def __init__(self, history_flat_dim: int = 162, embed_dim: int = 64):
        self.embed = nn.Sequential(
            nn.Linear(history_flat_dim, embed_dim * 2),
            nn.ReLU(),
            nn.Linear(embed_dim * 2, embed_dim),
        )
    def forward(self, betting_history: torch.Tensor) -> torch.Tensor:
        if betting_history.dim() == 3:
            betting_history = betting_history.flatten(start_dim=1)
        return self.embed(betting_history)
Flattening an 18×13 sequence before embedding destroys positional information. The network cannot distinguish "bet-check-bet" from "check-bet-bet" — both produce the same flattened input if the action one-hots happen to sum identically. In 6-Max with 4 streets and up to 18 actions per street, this is a critical expressiveness bottleneck. Libratus and Pluribus both use recurrent or attention architectures over betting histories.
src/training/cfr_buffer.py — network capacity for 6-Max
RegretValueNetwork and AverageStrategyNetwork are 3-layer MLPs with hidden_dim=512. The state space of 6-Max NLHE is approximately 10^160 information sets. The observation dimension for 6-Max with the current config is 354 (from features.py). A 512-wide MLP cannot generalize across:

6 distinct seat positions with asymmetric information
All four streets simultaneously
Multi-way pots with partial fold sequences
The card_abstraction.py suit isomorphism reduces hole cards from 1,326 to 169 canonical hands, which is correct. However the equity bucketing (HandStrengthBucket) uses cdist + linear_sum_assignment — both O(N²) and O(N³) operations — computed live during traversal rather than from the precomputed cache. For high-frequency traversal this will stall workers.

Replace HistoryEmbedding with the existing LSTMHistoryEncoder from sequential_history.py. Wire it into PokerActorCritic.__init__():

3. Data Throughput & Multi-GPU Scaling — Score: 10 / 25
src/training/parallel_cfr.py — the SyncManager bottleneck

class SharedRegretBuffer:
    def __init__(self, manager: mp.managers.SyncManager):
        self.regrets = manager.dict()      # ← This is the bottleneck
        self.lock = manager.Lock()
mp.managers.SyncManager proxies every dict access through a dedicated manager process via a Unix domain socket and Python pickle serialization. Each accumulate_regrets() call involves: pickle-serialize the update → send over socket → manager acquires lock → updates nested dict → sends acknowledgment → caller deserializes. At 8 workers each writing 100+ regret updates per second, this becomes the dominant bottleneck — measured overhead is typically 10-50ms per call at this access pattern.
The correct approach for high-throughput regret aggregation is torch.multiprocessing shared tensors (zero-copy) or numpy arrays in multiprocessing.shared_memory. Workers accumulate locally and the master aggregates periodically:

# Proposed pattern
import multiprocessing.shared_memory as shm
import numpy as np

# Master allocates a fixed shared tensor for regrets
# Workers write to their own slice; master reduces at iteration boundary
shared_regrets = torch.zeros(num_infosets, num_actions).share_memory_()
src/training/cfr_buffer.py — reservoir sampling under load

class RegretBuffer:
    def __init__(self, buffer_size=10000, num_actions=12):
        self.samples: list[RegretSample] = []
        self.reservoir_count = 0
    
    def add_sample(self, ...):
        j = np.random.randint(0, self.reservoir_count + 1)
        if j < self.buffer_size:
            if len(self.samples) < self.buffer_size:
                self.samples.append(sample)
            else:
                self.samples[j] = sample  # Random list index write
This is single-threaded Python with no locking. If ParallelCFR workers call add_sample() concurrently (which happens through the SyncManager proxy), the reservoir_count counter race condition will cause incorrect reservoir probability distribution — some samples will be systematically over-represented.
sample_batch() calls torch.stack(obs_list) inside the batch loop — this allocates a new tensor for every mini-batch. For a buffer with 10,000 entries and frequent sampling, this creates significant GC pressure. A pre-allocated tensor batch cache would be appropriate.
GPU utilization from workers
Workers in _worker_process() perform only CPU-side random action selection. There is no GPU inference in the traversal loop — the network is never called from workers. This means the main GPU sits idle during traversal phases. The correct architecture (as used in AlphaGo and Pluribus implementations) is a centralized GPU inference server: workers send batched observation tensors over shared memory, the GPU server returns action distributions, workers consume them. This requires restructuring MCCFRTraversal to batch network calls rather than calling the network per-step.
src/training/buffer.py — consolidated tensor allocation
_consolidate_tensors() in RolloutBuffer calls torch.stack() once per key across all N steps — this is correct and efficient. This part of the pipeline is well-implemented.

This is a reasonable approximation but there are two issues. First, the pot reference includes amount_to_call added twice (once explicitly, once inside the parenthetical) — this is the correct "pot after call" formula, so it is actually fine. Second, and critically, the bet sizing is uniform across all streets. Superhuman bots use street-specific, SPR-dependent bet sizing trees. On the river with SPR < 2, a 2x pot overbet is geometrically correct; preflop with 100BB effective, a 2.5x pot bet is almost never the right sizing bucket.
src/env/wrappers.py — linear interpolation mapping

def _map_our_action_to_rlcard(self, action, legal, ctx):
    ...

When RLCard exposes only 3 raise levels but our action space has 8 raise buckets, this linear interpolation collapses multiple distinct bet sizes to the same RLCard action. The network learns to differentiate between RAISE_HALF_POT and RAISE_FULL_POT internally, but they both map to the same executed action. The network's gradient signal for bet sizing is therefore corrupted — losses associated with different bet sizes train against identical environmental outcomes.
Missing: geometric bet sizing trees
Pluribus used a per-street bet sizing abstraction of the form {0.5x, 1x, All-In} on the river and {0.25x, 0.75x, All-In} on earlier streets, selected to minimize information loss rather than linear coverage. The correct approach is to define a BetSizingTree per street and SPR bucket, then map our 12 discrete actions onto whichever tree node is active. The current uniform 12-action space over-represents large overbets (which are rare) and under-represents the nuanced small-bet range (33%–75% pot) where most GTO play occurs.
